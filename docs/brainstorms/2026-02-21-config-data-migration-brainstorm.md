# 导入导出配置与数据（整机迁移）Brainstorm

## What We're Building
为 PaperMemory 增加“整机迁移”能力：用户可导出一个单一 JSON 迁移包，并在新设备一键导入。迁移包将同时包含论文数据（Memory）与配置数据（含敏感凭证），以实现最小迁移成本。

导入行为采用“直接覆盖”语义：导入后本地现有数据被替换为迁移包内容，不做合并。系统在导入时执行版本兼容检查，优先尝试兼容迁移（复用现有数据迁移逻辑）；仅在迁移失败时阻止导入。

## Why This Approach
需求目标是“整机迁移”，核心优先级是“一次完成、操作最少、认知负担低”。在该前提下：
- 单文件 JSON 比多文件或压缩包更简单，最符合用户预期。
- 覆盖导入比合并导入更可预测，避免冲突规则带来的复杂度。
- 不加密导出减少流程摩擦，符合当前用户明确偏好。
- 版本不一致时“尽量迁移”可显著提升迁移成功率，同时保留失败兜底。

该方案遵循 YAGNI：先满足单用户整机迁移，不引入团队共享、分级包体、复杂冲突解决等超前设计。

## Key Decisions
- 目标场景：整机迁移（新设备一键恢复），不是团队共享。
- 导出内容：包含数据 + 配置 + 敏感凭证（GitHub PAT / Notion Token / AI API Key）。
- 导入策略：直接覆盖当前本地数据。
- 文件形态：单一迁移文件（`PaperMemory-migration.json`）。
- 安全策略：不加密导出文件（由用户自行保管文件）。
- 兼容策略：版本不一致时先尝试兼容迁移，失败才阻止导入。

## Resolved Questions
- 主要目标：整机迁移。
- 是否包含敏感凭证：包含。
- 导入时冲突处理：直接覆盖。
- 导出文件是否加密：不加密。
- 文件结构：单文件。
- 版本不兼容处理：尽量迁移，失败阻止。
